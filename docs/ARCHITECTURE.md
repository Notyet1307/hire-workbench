# 架构与扩展位置

## 当前选择

用一个 TypeScript 项目承载中文界面、API、任务执行与文档分析。Node.js 24 提供 SQLite 能力；首版不要求独立数据库或消息队列。前端构建后由同一服务提供，开发时 Vite 将 API 请求转发到后端。

选择独立 MVP 是为了先验证中文岗位标准、简历证据和人工复核。它不能替代完整 ATS 的协作、权限、招聘门户和运营功能。以后决定接入 Harly 时，需要显式迁移业务实体，而不是假设二者数据结构相同。

## 共享契约

`src/shared/types.ts` 定义前后端共用的实体与状态。

| 实体 | 关键关系或不变量 |
|---|---|
| `Job` | 保存 `criteria` 和 `version`；标准修改后产生新版本 |
| `Candidate` | 保存正文、解析状态和整份候选资料的 `resumeVersion`；每次保存递增 |
| `Application` | 唯一关联 `jobId + candidateId`，拥有招聘阶段 |
| `AnalysisTask` | `queued → running → succeeded / failed`，记录次数与错误 |
| `Analysis` | 保留 `jobSnapshot`、`resumeSnapshot`、版本和模式 |
| `Assessment` | 对应一项标准，拥有状态、解释、原文与追问 |
| `Evidence` | `quote` 与原文位置 `start / end` 一致 |
| `Review` | 保存人工决定，可关联具体分析版本 |
| `Interview` | 关联应聘记录，保存排期与结果 |
| `AuditEvent` | 留存本工作区的重要业务操作 |

任务重试使用原任务输入快照。用户修改简历或岗位后，应新建分析，不能将旧任务标记为已经采用新输入。

首版的 `resumeVersion` 是候选资料快照版本名。只修改联系方式也会递增；若正文变化，当前记录的源文件名会清空，避免将手工修改后的文本仍标作上传原文件。历史分析不受影响。

## 请求到结果

1. HTTP 边界校验输入，保存岗位、候选人和关联记录。
2. 分析请求读取并固定当前输入版本，持久化任务，返回任务标识。
3. 后台执行分析。规则和模型使用同一种输出类型，但记录各自模式和引擎。
4. 模型结果经过结构和原文校验。不可验证的引文不能成为成功证据。
5. 保存分析及输入快照，前端读取完成状态并显示证据。
6. 人工复核保存独立记录，并按决定推进招聘阶段。

前端只在有执行中任务时轮询工作区。非成功响应显示真实错误，不用前端内存伪造保存结果。

## 文档与分析边界

`src/server/parse.ts` 负责从文件获得文本，返回可分析或待补充正文状态。解析层不负责招聘评价。没有正文时，后续分析必须停止并提示。

`src/server/evaluation.ts` 接受 `EvaluationInput`，返回 `EvaluationResult`。规则模式在本地执行；模型模式通过 `ProviderConfig` 访问外部 Chat Completions 服务。提示输入尽量只包含岗位标准与简历正文，避免额外发送联系方式字段。

Harly 文档模块提供 Unicode 文本可读性检查、文档分块及 OCR 接口边界。其原评分逻辑没有原样移入本项目；中文评价由本项目实现。具体复用文件、来源版本及许可证见根目录 `THIRD-PARTY-NOTICES.md`。

默认规则应保守地表达证据强弱。评分、覆盖率和展示解释需要来自同一份结果，不能分别在前端重算而产生矛盾。

模型输出格式默认 `json_object`，可按提供商能力选择 `json_schema`；两种路径均经过 Zod 和原文证据校验。评分对已知评价项做加权平均，未知项不进入分母，覆盖率另算。规则模式只产生部分满足或信息不足，分数经常为 50，不用于宣称排名效果。

## 持久化与访问范围

SQLite 放在 `DATA_DIR/workbench.sqlite`，运行时可能伴随 WAL/SHM 文件。上传后只保存提取正文、源文件名和版本，不存储原 PDF/DOCX 二进制。这是单进程、单工作区的部署形态。开发和测试通过不同端口及不同数据目录隔离，禁止两个实例同时操作同一个数据目录。

默认监听 `127.0.0.1`。非本机监听要求配置访问口令。配置了访问口令后，登录会话使用 HttpOnly cookie。跨来源写入需要被拒绝。该设计不等同于企业身份、租户隔离或细粒度 RBAC。

工作区导出排除服务端秘密。它是业务数据留档，不能自动恢复。备份前停止服务，再复制整个数据目录，避免遗漏 SQLite 辅助文件。

## 扩展时改哪里

| 下一步 | 建议边界 | 必须保留的行为 |
|---|---|---|
| 新模型提供商 | 服务端 ProviderConfig 与模型请求边界 | 明确失败、结构校验、引用校验、真实模型名 |
| OCR | `parse.ts` 的文档处理边界 | 未识别内容不能伪装成有效简历；原文可追溯 |
| 新评价维度 | `Criterion` 和服务端评价逻辑 | 版本快照、四种状态、证据和追问 |
| 团队协作 | 身份与数据访问边界 | API 与页面同时授权，复核人不可任意冒用 |
| PostgreSQL | 持久化层 | 迁移与备份、关联唯一性、旧分析不可变 |
| Go 文档服务 | 经验证有独立负载后拆分文档接口 | 保持文件校验、任务状态与原文坐标语义 |
| Harly 集成 | API 或显式迁移层 | 对照实体和权限，不能直接套用另一套表结构 |

## 设计取舍

- 先用 SQLite 减少首次启动依赖，接受首版不覆盖大规模并发和多租户。
- 先把证据、版本和人工复核做成领域数据，避免后期只靠提示词补丁补回可追溯性。
- 不引入独立 Agent 编排平台，当前任务与模型接口已覆盖首版流程。
- 将规则结果明确标识，保证没有模型密钥时仍可运行，且不误导为真实模型评估。
- 使用同一组测试和验证脚本支撑开发与 pstack 接手，避免出现两套验收真相。
