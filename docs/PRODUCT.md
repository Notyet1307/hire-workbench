# 产品范围

## 首版解决什么问题

招聘者希望把“看起来不错”的简历判断拆成可以核对的岗位标准与原文证据，再把缺少的信息转成面试问题。本版本围绕这个目标提供一条可运行的工作流。

参考方向来自 [WhaleHire 产品说明](https://whalehire.docs.baizhi.cloud/node/019b26a0-d113-779b-a84c-e2867e024324)。本项目自行实现交互与业务代码，不主张复刻其全部功能、视觉素材或商业服务。

## 变量、关系、约束

核心变量是岗位、标准、候选人、简历版本、应聘记录、分析任务、分析结果、人工复核和面试。

候选人通过应聘记录关联到岗位。一份分析引用特定版本的岗位与简历。分析给出逐项判断和证据，复核记录招聘者的决定。面试沿用同一条应聘记录。

约束是能还原当时输入、区分信息缺失与能力缺失、显示失败原因、保留人工决定。模型本身不拥有拒绝或录用权限。

## 已纳入首版的范围

| 工作 | 用户获得什么 |
|---|---|
| 岗位与评价标准 | 创建和修改岗位；配置权重、必需项和关键词；保留版本 |
| 人才库 | 添加和修改候选人、标签和简历正文 |
| 简历导入 | PDF、DOCX、TXT 文本提取；无可用正文时明确提示补充 |
| 岗位关联 | 同一候选人可针对不同岗位独立分析和推进 |
| 分析任务 | 可见排队、执行、成功和失败；支持失败重试 |
| 证据评价 | 四种状态、分数、覆盖率、原文引用及追问 |
| 人工复核 | 复核人与说明留档，决定推进、暂缓或不推进 |
| 面试记录 | 安排时间、面试人、地点、备注与结果 |
| 留档 | 分析 JSON、工作区 JSON、操作记录 |
| 本地持久化 | SQLite 保存业务数据和提取正文，正常重启保留内容 |

准确验收范围与当前限制以 [测试报告](TEST-REPORT.md) 为准。这里描述功能边界，不替代逐项验收证据。

## 两种分析模式

**规则模式**用于无密钥启动和流程验证。它寻找与评价标准关键词相关的文本，按保守规则形成结果。命中只是证据候选，不等于证明能独立完成工作。该模式不是语义检索，也不是完整招聘决策模型。

**模型模式**调用服务端配置的兼容 API。结构化输出经解析和证据校验后才保存为成功结果。接口失败、超时或不合法输出作为失败任务显示。模型质量需要在真实样本上另外评估。

## 如何理解结果

| 状态 | 含义 |
|---|---|
| 明确满足 | 输入材料对该标准提供了可核对的支持 |
| 部分满足 | 有相关证据，但职责、深度或范围仍需确认 |
| 明确不满足 | 有直接证据支持不满足该标准 |
| 信息不足 | 当前材料不足以判断 |

分数是已知评价项的加权平均，`unknown` 不进入评分分母。覆盖率单独表示有可判断证据的标准所占权重。全部未知时分数为空，不能把它伪装成零分或满分。

规则模式保守地产生部分满足或信息不足，因此分数经常为 50。这是规则语义的结果，不代表候选人排序质量。分数不能脱离覆盖率、逐项证据和当前模式单独使用。规则模式和模型模式的结果也不应直接混成同一排行榜。

“必需项”用于突出需要重点核实的条件，不是自动拒绝开关。岗位标准本身需要招聘者确认，避免把不相关的个人特征当作能力指标。

## 明确未完成的范围

- 扫描件 OCR、图片简历与复杂版式还原。
- 原始 PDF/DOCX 二进制归档。当前只保留提取正文、文件名和版本。
- 企业级多用户、组织权限、SSO 和客户隔离。
- 招聘网站自动投递、外部人才搜索、邮箱或即时通信同步。
- 完整 Offer 审批、签约和入职流程。阶段名称存在不代表这些系统已经实现。
- 大规模人才库向量检索、排名学习和模型微调。
- 生产级可用性、并发容量、备份恢复演练和长期运维验证。
- 自动恢复工作区 JSON、完整 Harly 数据迁移与双向同步。
- Go 服务拆分和用户的 Mac mini、devbox、Codync、Magpie 实际接入。

这些项目应按需求逐个验证和实现，不能仅靠增加菜单或接口占位符宣称完成。
